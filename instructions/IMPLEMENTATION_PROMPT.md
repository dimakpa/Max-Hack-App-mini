# Задание для агента реализации: ТехЗаказ MVP для MAX

## Режим работы

Ты реализуешь работающий хакатонный MVP, а не только макет или план. Исходные требования находятся в `TZ.md` в корне репозитория. Прочитай его полностью и считай источником правды. Если текущая кодовая база уже содержит заготовки, сначала изучи их и продолжи в принятом стиле. Не удаляй и не откатывай чужие изменения.

Работай до воспроизводимого локального результата: реализуй сервисы, запусти их, выполни тесты, проверь основной сценарий, подготовь инструкции и затем останови запущенные процессы. Не заявляй, что что-либо работает, без фактической проверки. Когда требование невозможно проверить локально, так и напиши в итоговом отчете.

Не расширяй продукт за границы `TZ.md`: не добавляй оплату, договоры, реальную верификацию компаний, вакансии, поиск работников, карты/GPS, CRM, внешние каталоги, рекламу или тарифы. `ТехСмена` - только возможное развитие в документации, не функция MVP.

## Важный секрет

В корне может находиться `token_max.md`. Это секретный локальный файл с токеном бота.

- Не открывай, не печатай, не копируй и не добавляй его в контекст, код, Docker image, README, презентацию, тестовые фикстуры или логи.
- Добавь `token_max.md`, `.env` и секретные варианты переменных окружения в `.gitignore`.
- Создай только `.env.example` с пустым `MAX_BOT_TOKEN=` и пояснением, откуда оператор вручную задает переменную.
- Приложение не должно читать `token_max.md` само. Токен передается оператором через окружение.

## Цель MVP

`ТехЗаказ` - B2B-сервис в MAX для малого подрядчика в Чебоксарах и Чувашской Республике. Он заказывает спецтехнику только с экипажем. Пользователь описывает задачу текстом либо заполняет короткую форму, проверяет извлеченные параметры, получает подходящие предложения, выбирает поставщика, а диспетчер подтверждает/отклоняет и меняет статус. После завершения заказчик оставляет один отзыв.

Пилотные категории ровно такие:

1. Автокран.
2. Трактор с навесным оборудованием.
3. Самосвал КамАЗ.
4. Экскаватор-погрузчик.

Используй не менее трех вымышленных поставщиков `Поставщик А`, `Поставщик Б`, `Поставщик В` и не менее восьми единиц техники. Все названия, цены, рейтинг, доступность, отзывы и изображения должны быть синтетическими. Не выдавай рейтинг за верифицированный MAX или внешним сервисом. Не используй реальные компании, логотипы или фотографии без явных прав.

## Обязательный результат

Собери монорепозиторий с отдельными сервисами и явными границами:

- `frontend` - React mini app на TypeScript.
- `backend` - TypeScript API и бизнес-правила.
- `bot` - сервис чат-бота MAX и адаптер уведомлений.
- `db` - PostgreSQL как отдельный контейнер в Docker Compose, а не встроенная база в frontend/backend.

Выбирай минимальный поддерживаемый стек после проверки текущего репозитория. Если стек еще не задан, предпочтительны React + Vite + TypeScript для frontend, TypeScript HTTP API с валидацией входных схем, PostgreSQL и официальный совместимый способ работы с API MAX для бота. Зафиксируй выбранные версии зависимостей и lockfile. Не подключай зависимость только ради одной строки кода.

Создай:

- `compose.yaml` или `docker-compose.yml` со службами `db`, `backend`, `frontend`, `bot`;
- Dockerfile для каждого исполняемого сервиса, `.dockerignore`, healthcheck там, где это уместно;
- миграции и seed с воспроизводимыми тестовыми данными;
- `.env.example` без настоящих секретов;
- корневой `README.md` и каталог `docs/` из раздела "Документация" ниже.

Один понятный сценарий должен поднимать локальную систему: `docker compose up --build`. Не загружай и не собирай внутри Docker image локальную LLM: базовый запуск обязан работать без модели и без токена MAX. Docker build должен быть предсказуемым и не зависеть от скрытых локальных файлов.

## Архитектура и локальный режим

### Режимы запуска

Предусмотри два явно разделенных режима.

**Локальный demo-режим** нужен для разработки и QA:

- mini app открывается в обычном браузере;
- доступны фиксированные тестовые роли заказчика и диспетчера;
- все данные тестовые;
- бот не делает реальных вызовов MAX без токена, а адаптер уведомлений записывает тестовое уведомление в БД или лог и позволяет проверить его через интерфейс/API;
- отсутствует неявный доступ "от имени пользователя";
- этот режим включается только явной безопасной переменной окружения, например `DEMO_AUTH=true`, и должен быть выключен по умолчанию в production-конфигурации.

**MAX/staging-режим** нужен для последующего подключения:

- frontend использует текущий MAX Bridge только внутри клиента MAX;
- backend получает `initData`/`WebAppData` и валидирует его на сервере по актуальному алгоритму MAX до любых действий от имени пользователя;
- token бота берется только из `MAX_BOT_TOKEN`;
- URL mini app и webhook задаются отдельными переменными `PUBLIC_APP_URL` и `PUBLIC_API_URL`;
- production webhook и мини-приложение требуют публичный HTTPS с сертификатом доверенного центра;
- локальный `http://localhost` нельзя объявлять проверкой работы внутри MAX. Для реальной проверки понадобятся публичный HTTPS URL и настройки бота в MAX.

Не реализуй Kubernetes сейчас. Добавь только короткий документ, что потребуется для следующего этапа деплоя: образы, внешняя PostgreSQL/volume, переменные и ingress с TLS.

### MAX-интеграция

Перед реализацией перечитай актуальные официальные документы MAX, в первую очередь:

- `https://dev.max.ru/docs/webapps/introduction`
- `https://dev.max.ru/docs/webapps/validation`
- `https://dev.max.ru/docs/webapps/bridge`
- `https://dev.max.ru/docs/chatbots/bots-coding/prepare`

Не придумывай названия методов или payload MAX. Используй реальные актуальные API и задокументируй дату проверки. Если API/SDK не доступен в локальной среде, сохрани адаптер с четким интерфейсом и реализуй dry-run, но не выдавай это за живую интеграцию.

Бот должен поддерживать минимум:

- приветствие и кнопку/ссылку на mini app;
- уведомление диспетчера о новой заявке;
- уведомление заказчика о `CONFIRMED`, `DECLINED`, `COMPLETED`;
- контекстный переход к заявке или отзыву;
- уведомление поставщика о запросе обратного звонка, без запуска и записи звонка.

Не передавай персональные данные в deep link. Передавай только неприватный ID заказа либо серверный одноразовый ключ и повторно проверяй права на backend.

## Модель данных и API

Минимально нужны сущности: пользователь/роль, поставщик, техника, доступность техники, заявка/заказ, отзыв, заявка поставщика и тестовое уведомление. Названия таблиц и полей выбери последовательно, добавь ограничения БД и миграции.

Заказ хранит параметры задачи, выбранное предложение/технику/поставщика, текущий статус, историю значимых изменений и причину отклонения при необходимости. Отзыв может быть только один на один завершенный заказ. Заявка поставщика хранит статус `SUBMITTED`, `APPROVED` или `REJECTED`; публичная админка не нужна.

Статусная машина должна находиться в backend, а не только в UI:

| Текущий статус | Разрешенные изменения |
| --- | --- |
| `NEW` | `CONFIRMED`, `DECLINED` диспетчером выбранного поставщика |
| `CONFIRMED` | `IN_PROGRESS` диспетчером, `CANCELLED` в предусмотренном MVP порядке |
| `IN_PROGRESS` | `COMPLETED` диспетчером |
| `COMPLETED`, `DECLINED`, `CANCELLED` | переходов нет |

API обязан на сервере проверять роль, принадлежность диспетчера поставщику, доступность выбранной единицы и текущий статус. Обработай повторный клик/повторный запрос идемпотентно: не создавай второй заказ, повторное действие должно вернуть актуальное состояние или понятную контролируемую ошибку. Все внешние входные данные валидируй схемой на backend. Не доверяй полям роли, цены, статуса и поставщика из браузера.

Сделай документированное REST API или другой ясный транспорт. Нужны как минимум операции:

- получить/создать черновик из текста;
- проверить и сохранить параметры заявки;
- получить предложения;
- выбрать предложение и создать заказ;
- список и детали заказов для заказчика/диспетчера;
- изменения допустимых статусов;
- запрос обратного звонка;
- создать отзыв;
- подать заявку поставщика;
- health/readiness endpoint без секретов.

## ИИ-помощник без блокировки MVP

ИИ работает только с текстом. Не реализовывай распознавание голоса, загрузку аудио или транскрибацию.

Из текста он формирует черновик:

- категория техники;
- дата и время;
- длительность;
- населенный пункт;
- описание работ;
- ключевые ограничения.

Пользователь всегда видит и подтверждает/правит все поля. Неуверенно извлеченное поле оставляй пустым, а не придумывай значение. ИИ не бронирует технику, не назначает цену, не гарантирует доступность и не меняет заказ.

Реализуй провайдерный интерфейс для помощника:

1. `mock`/детерминированный провайдер по умолчанию для Docker, E2E и офлайн-демо. Он должен обрабатывать подготовленные русскоязычные примеры воспроизводимо.
2. Опциональный локальный провайдер для совместимого runtime, например Ollama, по URL из окружения. Он не должен требовать скачивания модели при `docker compose up`. Название модели конфигурируется, возможные кандидаты - квантованные `Qwen3 8B` и `Qwen3 4B`.

Не утверждай, что конкретная модель стабильно работает на Mac с 24 ГБ памяти, пока не проведен отдельный замер. В `docs/AI_BENCHMARK.md` подготовь способ измерения двух задач: JSON-разбор русской заявки и ранжирование восьми предложений, с фиксацией качества, задержки и ошибок. Сам основной MVP обязан работать с `mock`, если модель выключена или упала.

Подбор раздели на две части:

1. Детерминированно отсей технику, не совпадающую по категории, региону или доступности.
2. Ранжируй остаток по релевантности тексту, времени подачи, цене смены и рейтингу поставщика. Покажи человеку краткое объяснение результата, например "подходит по типу техники и времени подачи".

При недоступности модели переводи пользователя на ручную форму и прозрачную обычную сортировку. Отсутствие ИИ не должно ломать создание заказа.

## Интерфейс mini app

Интерфейс нужен для реальной задачи на мобильном и desktop, не лендинг. Используй актуальные MAX UI и MAX Bridge, когда они доступны и подходят; не копируй закрытые ассеты или интерфейсы конкурентов пиксель-в-пиксель. Сохрани узнаваемую для MAX простоту: чистая светлая рабочая поверхность, компактная навигация, ясные статусы и действия, системные отступы и контраст. Не используй темную оранжево-черную эстетику со скриншотов конкурентов, декоративные градиенты, орбы, маркетинговый hero или лишние вложенные карточки.

Обязательные экраны и состояния:

1. **Новая заявка** - первый экран с выбором `Описать задачу` или `Заполнить вручную`, без общего каталога на старте.
2. **Проверка черновика** - текст задачи и извлеченные поля с возможностью исправить каждое поле.
3. **Ручная форма** - категория, место, дата/время, длительность, описание и ограничения. Обязательные поля валидируются до отправки.
4. **Предложения** - 3-5 подходящих вариантов с техникой, поставщиком, ценой смены, временем подачи, доступностью, рейтингом и объяснением позиции. Заказчик может изменить фильтры и выбрать любой вариант.
5. **Карточка и подтверждение заказа** - выбранные параметры, поставщик, понятное подтверждение отправки.
6. **Мои заявки** и **Заявки поставщика** - фильтр по статусу, детальная карточка и только допустимые действия для роли.
7. **Отзыв** - доступен только заказчику и только после `COMPLETED`; оценка 1-5 и короткий текст.
8. **Стать поставщиком** - компания, регион, контакт, категории; после отправки `На проверке`.
9. Состояния загрузки, пустого списка, ошибки, успеха, отсутствия предложений, недоступной техники и отключенного ИИ.

Добавь в demo-режим явный, но ненавязчивый признак тестовых данных/тестовой роли. Для dev-only переключения ролей не создавай возможность войти под другой ролью в production.

Используй доступные библиотечные иконки для иконок-кнопок. Кнопки должны быть удобны на телефоне, а текст не должен обрезаться или пересекаться. Проверь как минимум viewport `375x812` и `1440x900` реальным браузерным прогоном и сохрани проверочные скриншоты вне исходного кода либо в понятном QA-артефакте, если это не загрязняет репозиторий.

## Безопасность и данные

Минимальные требования:

- серверная HMAC-валидация актуальных launch data MAX; `initDataUnsafe` нельзя использовать как доказательство личности;
- в production без валидных данных MAX доступ к защищенным действиям запрещен; demo-обход допустим только при явной dev-настройке;
- токены, пароли и личные данные не попадают в frontend bundle, API-ответы, error tracking и логи;
- параметризованные запросы/ORM, серверная валидация схем, ограничения длины строк и понятные сообщения об ошибках;
- права заказчика/диспетчера проверяются на каждом изменяющем endpoint;
- CORS разрешает только явно заданный публичный frontend origin в staging/production;
- добавь разумный rate limit для публичных изменяющих endpoints, если выбранный стек позволяет сделать это без избыточной сложности;
- не рендери пользовательский текст как HTML;
- пользовательский контент (задачи, отзывы, заявки поставщиков) в MVP тестовый. Документируй, что до публичного запуска нужны условия, политика обработки данных, контакт поддержки и модерация/удаление незаконного контента;
- зависимости фиксированы, а базовая проверка уязвимостей запускается и ее результат честно отражен в отчете.

Сделай `docs/SECURITY_CHECKLIST.md` с тем, что проверено автоматически, что проверено вручную, и что остается условием публичного запуска. Не заявляй о соответствии законам или полноценном pentest.

## Тестирование и фактическая проверка

Покрой рисковые бизнес-правила тестами. Выбери локальные инструменты, совместимые со стеком, и добавь команды в README. Минимально нужны:

- unit-тесты статусной машины, ролей, запрета повторного отзыва, проверки доступности и детерминированного ранжирования;
- unit/contract тесты разбора текста с пустыми неуверенными полями и fallback при ошибке ИИ;
- API integration-тесты основных изменяющих сценариев с тестовой БД;
- E2E в браузере для основного пути двумя ролями: заказчик -> текст/ручная форма -> предложения -> заявка -> диспетчер подтверждает -> `IN_PROGRESS` -> `COMPLETED` -> один отзыв;
- E2E/интеграционные негативные случаи: обязательное поле, нет предложений, недоступная техника, повторная обработка, недопустимый статус, повторный отзыв, недоступный ИИ;
- smoke-проверка `docker compose up --build`, healthchecks, миграций и seed;
- проверка адаптера уведомлений в dry-run; реальную доставку MAX отдельно пометь как требующую токен и публичный HTTPS.

После изменений действительно выполни доступные тесты. Исправь обнаруженные ошибки. Заверши работу остановкой локальных сервисов (`docker compose down` или эквивалент) после получения результатов, если пользователь прямо не попросит оставить их запущенными.

## Критерии приемки реализации

Работа считается готовой локально только если одновременно выполнены следующие пункты:

- [ ] `docker compose up --build` поднимает PostgreSQL, API, frontend и bot без обращения к `token_max.md` и без обязательной LLM.
- [ ] Миграции и seed создают трех вымышленных поставщиков, минимум восемь единиц техники и воспроизводимые тестовые роли.
- [ ] Заказчик может пройти сценарий от текста/ручной формы до выбора предложения и создания `NEW` заявки.
- [ ] Диспетчер именно выбранного поставщика может подтвердить/отклонить заявку и провести ее `CONFIRMED -> IN_PROGRESS -> COMPLETED`.
- [ ] Заказчик может оставить один отзыв только после завершения заказа.
- [ ] Недопустимые переходы, повторное действие, повторный отзыв и выбор недоступной техники не меняют данные некорректно.
- [ ] При выключенном/ошибающемся ИИ ручной сценарий и выдача предложений продолжают работать.
- [ ] Есть форма заявки поставщика со статусом `SUBMITTED`; новая компания не попадает в каталог автоматически.
- [ ] Уведомления проходят через проверяемый dry-run адаптер; ограничения настоящего MAX явно зафиксированы.
- [ ] UI проверен на mobile и desktop, включая loading/empty/error/success состояния.
- [ ] В production-конфигурации нет demo-обхода и есть серверный путь валидации данных MAX.
- [ ] Нет токенов и личных данных в tracked-файлах, `.env.example`, образах и выводе тестов.
- [ ] Все доступные тесты и Docker smoke-run выполнены; их результат сохранен в финальном отчете без преувеличений.
- [ ] README и документы из раздела выше позволяют другому человеку повторить запуск и QA.
