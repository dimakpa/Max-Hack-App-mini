# QA checklist

Результат каждого пункта ручного прогона отмечается проверяющим, а не заполняется заранее. Общие предусловия: чистый локальный demo seed, `docker compose up --build`, браузер без сохранённой роли либо роль `customer`.

## Запуск

1. Выполнить `docker compose up --build`. Ожидание: `db`, `backend`, `bot`, `frontend` переходят в `healthy`, миграция и seed не требуют MAX/LLM. Требование: `TZ.md` §8, §13–14.
2. Открыть `/health` backend, bot и frontend, затем backend `/ready`. Ожидание: нет секретов и диагностических stack trace. Требование: `TZ.md` §8–9.
3. Перезапустить Compose без удаления volume. Ожидание: миграции/seed идемпотентны, три поставщика и девять машин не дублируются. Требование: `TZ.md` §7–8.
4. Проверить признак `Тестовые данные` и переключатель фиксированных ролей. Ожидание: они есть в demo и отсутствуют в production build. Требование: `TZ.md` §7–8.

## Заказчик

5. На первом экране проверить только два старта: `Описать задачу`, `Заполнить вручную`. Ожидание: нет общего каталога. Требование: `TZ.md` §5–6.
6. Ввести подготовленный русский текст. Ожидание: заполнены уверенные поля, все доступны для правки, заказ не создан. Требование: `TZ.md` §5–6.
7. Ввести неоднозначный текст без даты/категории. Ожидание: поля пустые, сервис ничего не придумывает. Требование: `TZ.md` §6, §9.
8. Открыть ручную форму и отправить с пустым описанием. Ожидание: браузер/API блокируют отправку и показывают поле. Требование: `TZ.md` §6, §9.
9. Заполнить четыре допустимые категории по очереди. Ожидание: используются только категории пилота. Требование: `TZ.md` §3.
10. Получить предложения в Чебоксарах. Ожидание: 3–5 вариантов при наличии, цена смены, подача, доступность, рейтинг и объяснение; можно выбрать не первый. Требование: `TZ.md` §5–6.
11. Выбрать вариант и подтвердить. Ожидание: отдельное подтверждение параметров, затем один заказ `NEW`. Требование: `TZ.md` §5–6.
12. Повторить тот же POST с `idempotencyKey`. Ожидание: тот же заказ и `replayed=true`, дубля нет. Требование: `TZ.md` §6, §9.
13. После `CONFIRMED` нажать запрос звонка дважды. Ожидание: один callback/outbox, повтор сообщает актуальное состояние. Требование: `TZ.md` §5–6.
14. После `COMPLETED` оставить рейтинг 1–5 и текст. Ожидание: отзыв виден в заказе. Требование: `TZ.md` §5–7.
15. Повторить отзыв. Ожидание: `409 REVIEW_EXISTS`, первый отзыв не меняется. Требование: `TZ.md` §6, §9.

## Диспетчер

16. Создать заказ Поставщика А, войти как `dispatcher-b`. Ожидание: заказ не виден; прямой URL/POST возвращает `403`. Требование: `TZ.md` §4, §6, §8.
17. Войти как `dispatcher-a`, открыть `NEW`, подтвердить. Ожидание: `CONFIRMED`, заказчику создано уведомление. Требование: `TZ.md` §5–6.
18. Выполнить `CONFIRMED → IN_PROGRESS → COMPLETED`. Ожидание: история содержит каждый переход, заказчик получает уведомление о завершении. Требование: `TZ.md` §5–6.
19. Попытаться `NEW → COMPLETED`. Ожидание: контролируемый `409`, статус не меняется. Требование: `TZ.md` §6, §9.
20. Отклонить новую заявку без причины, затем с причиной. Ожидание: без причины `422`, с причиной `DECLINED` и уведомление заказчику. Требование: `TZ.md` §5–6.
21. Повторно подтвердить `CONFIRMED`. Ожидание: актуальный заказ без второго события/уведомления. Требование: `TZ.md` §6, §9.

## Заявка поставщика

22. Отправить форму без категорий. Ожидание: отправка заблокирована. Требование: `TZ.md` §6.
23. Отправить валидную форму. Ожидание: статус `На проверке`/`SUBMITTED`, компания не появляется в suppliers/catalog. Требование: `TZ.md` §4, §6–7.

## ИИ и fallback

24. Запустить с `AI_PROVIDER=mock`. Ожидание: подготовленные русские примеры воспроизводимы. Требование: `TZ.md` §6, §8.
25. Запустить с `AI_PROVIDER=ollama` и недоступным URL. Ожидание: notice о fallback, ручная правка и подбор продолжают работать. Требование: `TZ.md` §6, §9.
26. Проверить, что подбор сначала исключает другую категорию, регион и недоступность. Ожидание: модель/ранжирование их не возвращает. Требование: `TZ.md` §6.
27. Дважды запросить одинаковый подбор. Ожидание: стабильный порядок при неизменных данных. Требование: `TZ.md` §6.

## Ошибки

28. Указать `Казань`. Ожидание: понятное пустое состояние и возврат к параметрам. Требование: `TZ.md` §3, §9.
29. Попытаться заказать seed-машину с `is_available=false` прямым API. Ожидание: `409 EQUIPMENT_UNAVAILABLE`, заказа нет. Требование: `TZ.md` §6, §9.
30. Создать перекрывающий заказ на ту же машину/время. Ожидание: второй заказ отклонён. Требование: `TZ.md` §6, §9.
31. Остановить backend во время UI-действия. Ожидание: понятная ошибка и `Повторить`, без пустого экрана. Требование: `TZ.md` §6, §9.

## Уведомления

32. Без `MAX_BOT_TOKEN` пройти новый заказ и статусы. Ожидание: уведомления получают `DELIVERED_DRY_RUN` и видны роли-получателю. Требование: `TZ.md` §5–6, §8.
33. Запросить звонок. Ожидание: диспетчер выбранного поставщика получает outbox-событие, звонок не запускается. Требование: `TZ.md` §5–6.
34. Проверить payload уведомления. Ожидание: только ID/одноразовый контекст, без телефона, имени или описания работ. Требование: `TZ.md` §8.

## Безопасность

35. Выключить `DEMO_AUTH`, отправить `x-demo-user`. Ожидание: `401 DEMO_AUTH_DISABLED`. Требование: `TZ.md` §8.
36. Отправить отсутствующий, изменённый, просроченный и дублированный `WebAppData`. Ожидание: `401` до бизнес-действия. Требование: `TZ.md` §8.
37. Проверить CORS с разрешённым и посторонним origin. Ожидание: браузерный доступ разрешён только перечисленному frontend. Требование: `TZ.md` §8.
38. Просмотреть bundle, API errors и логи. Ожидание: нет токена, DB password, пользовательских персональных данных. Требование: `TZ.md` §8.
39. Выполнить `npm audit` и container scan. Ожидание: результат сохранён честно; блокирующие уязвимости разобраны. Требование: `TZ.md` §8, §11.

## Responsive UI

40. Проверить 375×812: первый экран, форму, предложения, modal, список, drawer и отзыв. Ожидание: нет горизонтального overflow, перекрытия и обрезанных действий; touch targets доступны. Требование: `TZ.md` §6, §11.
41. Проверить 1440×900 те же шаги. Ожидание: рабочая область не растянута, sidebar и контент читаемы. Требование: `TZ.md` §6, §11.
42. Включить reduced motion и клавиатурную навигацию. Ожидание: focus виден, spinner не мешает, dialog закрывается кнопкой. Требование: `TZ.md` §6.

## MAX/staging

43. На публичном HTTPS открыть mini app через кнопку бота в web MAX. Ожидание: роль определена только после успешной серверной HMAC-проверки. Требование: `TZ.md` §5, §8.
44. Повторить в mobile MAX. Ожидание: Bridge доступен, основной сценарий и deep links работают. Требование: `TZ.md` §5, §8.
45. Отправить `/start`/`bot_started`. Ожидание: приветствие и ссылка на mini app. Требование: `TZ.md` §6.
46. Пройти заказ и статусы с реальными тестовыми MAX-аккаунтами. Ожидание: адресные уведомления без персональных данных в link. Требование: `TZ.md` §5–6, §8.
